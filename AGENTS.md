# Instrucciones obligatorias para agentes del backend

## Higiene del repositorio y README principal

- Está prohibido crear archivos, carpetas o documentos Markdown que no sean necesarios para un requisito, entregable, decisión técnica o mantenimiento verificable del proyecto. Antes de crear uno, comprueba si el contenido corresponde a un archivo existente; evita duplicados, borradores abandonados, notas temporales y documentación redundante.
- El `README.md` de la raíz debe presentar el proyecto con información necesaria para entender su propósito, estado real, arquitectura general, requisitos/instrucciones verificadas y enlaces a documentación especializada. No lo conviertas en un depósito de detalles internos, contratos extensos, ejemplos especulativos, contenido repetido de los roadmaps ni información ajena al uso y orientación general del repositorio.
- Al crear o actualizar un README, aplica [ENSAMBRIA_README_Documentation_Quality_Security_Standard.md](docs/rules/ENSAMBRIA_README_Documentation_Quality_Security_Standard.md), fuente normativa de su contenido, calidad y seguridad; no dupliques allí la documentación especializada.
- No omitas documentación requerida por las reglas: coloca el detalle en el documento normativo, roadmap, ADR o guía del módulo correspondiente y enlázalo desde el README raíz cuando sea útil.

## Ramas, verificación e integración

GitHub es el centro de calidad, seguridad, colaboración, trazabilidad y entrega desde Fase 0. Aplica [ENSAMBRIA_github_repository_governance_and_engineering_rules.md](docs/rules/ENSAMBRIA_github_repository_governance_and_engineering_rules.md) como fuente especializada, sin reemplazarla por una política genérica; estas instrucciones y [ARCHITECTURE_RULES.md](ARCHITECTURE_RULES.md) mantienen las obligaciones generales específicas de ENSAMBRIA. `main` se protege con Ruleset/Branch Protection; todo cambio, incluido documentación, entra mediante PR. No hagas push directo, force-push ni elimines `main`. Usa ramas breves y descriptivas (`feat/`, `fix/`, `refactor/`, `test/`, `docs/`, `security/`, `infra/`) por una unidad coherente; no crees ramas por archivo, no esperes a completar un backend ni mezcles objetivos sin razón técnica.

Todo PR declara alcance, criterios de aceptación, riesgos y evidencia conforme a la plantilla del repositorio; revisa diff y secretos, resuelve conversaciones y exige rama actualizada con `main` o merge queue equivalente. Aplica la regla original §8.1 cuando haya una sola persona mantenedora: la auto-revisión documentada permitida para cambios ordinarios no equivale a aprobación independiente ni elimina PR, checks o protección de rama. No simules aprobaciones humanas. Cambios críticos de seguridad, permisos, infraestructura o workflows requieren revisión independiente según disponibilidad de colaboradores. No integres con checks requeridos fallidos, pendientes, cancelados u omitidos. Tras integrar, verifica CI del commit exacto de `main`; ningún PR despliega a producción.

Ejecuta localmente el mismo punto de entrada y comandos que invoca GitHub Actions, con idénticos criterios. No ocultes errores, omitas checks ni afirmes que una suite pasó sin ejecutarla. Los comandos se adaptan a manifests y scripts realmente existentes. Aplica mínimo privilegio a GitHub Actions, fija acciones externas a SHA completo y define timeouts/concurrencia seguros. Las obligaciones de gobierno del repositorio y los controles operativos se detallan en [ENSAMBRIA_github_repository_governance_and_engineering_rules.md](docs/rules/ENSAMBRIA_github_repository_governance_and_engineering_rules.md); los requisitos arquitectónicos y específicos de ENSAMBRIA permanecen en [ARCHITECTURE_RULES.md](ARCHITECTURE_RULES.md). No afirmes que Rulesets, workflows o herramientas están configurados sin inspeccionarlos y verificarlos.

- `main` es la rama principal y debe mantenerse funcional y verificable. Para funcionalidades, refactorizaciones importantes, cambios de arquitectura, correcciones complejas o cambios de seguridad, trabaja en una rama descriptiva; por ejemplo `feat/key-rotation`, `fix/authorization-check`, `security/secret-encryption`, `refactor/key-service` o `docs/installation`.
- Todo cambio, incluidos los cambios triviales de documentación, se integra mediante PR; no omitas la protección de `main`.
- No hagas `push --force` sobre `main` ni reescribas historial compartido. No mezcles cambios sin relación; usa commits pequeños, coherentes y descriptivos. Nunca incluyas secretos, credenciales ni archivos locales sensibles.
- Antes de integrar cambios, revisa el diff y la presencia de secretos; ejecuta las pruebas y verificaciones relevantes del proyecto (incluidos formato y lints cuando apliquen). Compilar por sí solo no valida un cambio. Investiga y documenta fallos; no los ignores ni afirmes que una verificación pasó si no se ejecutó.
- Para cambios importantes, prepara un Pull Request con resumen, decisiones técnicas, pruebas ejecutadas y riesgos pendientes. No integres cambios con verificaciones obligatorias fallidas. Cambios sensibles de cifrado, autenticación, autorización o gestión de claves requieren la revisión exigida por el proyecto; el agente no debe fusionarlos automáticamente.
- El agente puede desarrollar, verificar y preparar ramas/PR de forma autónoma. Detente y solicita intervención cuando falten permisos, se requiera una decisión de seguridad importante o no sea posible validar la seguridad del cambio. No despliegues a producción ni ejecutes operaciones destructivas sin autorización explícita cuando corresponda.
- Mantén Rulesets/Branch Protection, checks obligatorios, historial auditable y estrategia de reversión; si falta permiso o función de GitHub, documenta el bloqueo en lugar de omitir la política.

Estas instrucciones aplican a todo el trabajo del repositorio, especialmente a los módulos, servicios y capas del proyecto. Son obligatorias junto con las instrucciones de niveles superiores y cualquier `AGENTS.md` más específico.

## Topología obligatoria y ownership de cuatro backends

ENSAMBRIA debe tener cuatro backends de dominio, cada uno como monolito modular, propietario único de sus reglas de negocio y datos, y con despliegue independiente:

- **CORE (`backend-core`):** identidad/autenticación, tenancy y contexto de seguridad, organizaciones/sucursales centrales, evaluación de entitlements, reservas, pagos, cargos transaccionales aprobados, ledger, liquidaciones y conciliación.
- **BUSINESS (`backend-business`):** operación de establecimientos, workforce, catálogo, clientes/CRM, membresías, inventario, Commerce/pedidos, marketing comercial, facturación de establecimientos, franquicias/regalías y comisiones de empleados.
- **PLATFORM (`backend-platform`):** control global y administración comercial de tenants, planes/suscripciones/facturación SaaS, políticas comerciales de ENSAMBRIA y tarifas de pagos/Marketplace.
- **PUBLIC (`backend-public`):** directorio, Discovery/Marketplace, páginas y proyecciones públicas autorizadas, reseñas y atribución del canal. No posee operaciones privadas, catálogo operativo ni inventario de los establecimientos.

El BFF público es una aplicación independiente que consume PUBLIC por gRPC; el BFF administrativo está integrado inicialmente en PLATFORM. ENSAMBRIA Business y Tenant Portal consumen el mismo BFF/API de producto; ENSAMBRIA App usa la superficie de producto y puede usar el BFF público para Discovery; Marketplace usa el BFF público; Platform Admin usa el BFF integrado en PLATFORM; Corporate publica contenido institucional estático o mediante una superficie pública autorizada. CORE no se expone directamente a frontends. Cada backend, BFF independiente y proyecto de interfaz mantiene artefactos, configuración y despliegue propios.

Tenancy técnica y gestión comercial de tenants son responsabilidades distintas: CORE posee identidad/contexto/aislamiento; PLATFORM administra la relación comercial; BUSINESS utiliza el contexto en la operación; PUBLIC solo recibe datos expresamente autorizados para publicar. BUSINESS es dueño de Commerce y de las reglas de las ventas; PUBLIC es dueño del canal Marketplace y de la atribución. PLATFORM define políticas de monetización; CORE valida y registra su efecto transaccional. BUSINESS conserva comisiones de empleados y regalías de franquicia.

Los cuatro backends no requieren cuatro bases PostgreSQL físicas desde el primer día. PostgreSQL compartido es válido con propiedad de datos, schemas/migraciones y roles/grants de mínimo privilegio por backend/dominio; ninguna credencial de runtime tiene acceso irrestricto a las tablas. Compartir infraestructura o conexión no autoriza consultas cruzadas. Cada módulo conserva modelos, casos de uso, puertos, adapters y pruebas propios, y consume otros dominios por contrato, no por tablas internas.

Todo frontend debe cumplir SEO/descubribilidad: las rutas web públicas y fichas publicadas de productos/servicios llevan SEO técnico/editorial completo; admin, páginas autenticadas, borradores y datos privados son `noindex` y no se incluyen en sitemaps ni datos estructurados públicos. BUSINESS posee contenido/fichas del tenant, PLATFORM el contenido institucional ENSAMBRIA y PUBLIC solo publica proyecciones explícitamente autorizadas. Las apps móviles cumplen ASO/deep links. Revisa [ARCHITECTURE_RULES.md](ARCHITECTURE_RULES.md) para los controles y ownership completos.

Aplica [ENSAMBRIA_Open_Graph_SEO_Metadata.md](docs/rules/ENSAMBRIA_Open_Graph_SEO_Metadata.md): la Fase 0 define contratos, ownership y criterios; la capacidad técnica base de SEO/metadata se implementa desde el primer corte ejecutable de Fase 1. Desde esa fase, completa SEO, Open Graph, metadata HTML inicial y pruebas al introducir cada ruta/contenido público; no difieras páginas públicas a fases posteriores para completarlas. Mantén rutas privadas, borradores y datos personales fuera de indexación, sitemaps y previews.

Los seis proyectos de interfaz no son backends adicionales: ENSAMBRIA Business y Tenant Portal usan los mismos contratos empresariales; App, Marketplace, Platform Admin y Corporate consumen únicamente superficies autorizadas para cada propósito. Las cuatro aplicaciones web usan React + TypeScript + Next.js; Business y App usan Flutter + Dart. No conviertas cada interfaz o módulo en microservicio: la arquitectura objetivo mantiene cuatro monolitos modulares con despliegues independientes. Las apps usan los BFF/contratos autorizados; CORE no se expone directamente a frontends, y Corporate no accede directamente a servicios de dominio. La Fase 0 define límites y contratos, pero no implica implementar simultáneamente los cuatro backends ni las seis aplicaciones; la ejecución sigue el roadmap y una extracción de módulo requiere necesidad demostrable y decisión documentada.

Los backends solo se comunican cuando un caso de uso realmente lo requiere:

- Usa **gRPC** para una consulta o comando síncrono que necesita respuesta inmediata.
- Usa **Outbox + NATS JetStream** para distribuir hechos ya persistidos que requieren procesamiento asíncrono y durable, reintento o replay.
- No uses eventos como RPC, no uses gRPC como sustituto de entrega durable y no generes llamadas/eventos cuando no existe una necesidad funcional.
- Nunca uses imports de implementación ni acceso cruzado a tablas como integración. Cada evento se valida y consume idempotentemente; cada RPC se autentica, autoriza, limita y correlaciona.

## Pruebas obligatorias por caso de uso y fase
## Ubicación del workspace y frontends

Antes de planificar o modificar una fase/subfase, consulta la sección de responsabilidades y evidencia de [ARCHITECTURE_RULES.md](ARCHITECTURE_RULES.md) y aplica la matriz obligatoria de casos de uso positivos, negativos, límites, duplicados/concurrencia, autorización, estados, fallos, integridad y privacidad. No basta con añadir una prueba feliz ni con medir cobertura de líneas.
El workspace Cargo del repositorio debe mantener un único manifiesto en `Cargo.toml` en la raíz del proyecto. La fase 0 verifica documentalmente la composición del workspace; la creación de crates/apps funcionales pertenece a las fases de implementación. Esta resolución compartida no mezcla bins, identidades, composición, ownership ni despliegues; cada módulo o frontend debe mantener límites claros y responsabilidades explícitas.
Las bibliotecas técnicas comunes de PostgreSQL/SQLx, transacciones/contexto RLS, gRPC/Protobuf, TLS/seguridad, errores, Redis, NATS Core/JetStream/Outbox, Vault y observabilidad se diseñan como dependencias neutrales, sin reglas de dominio. El composition root configura un pool PostgreSQL por proceso; los módulos co-residentes reciben ese pool y los procesos separados crean sus propios pools. Cada módulo conserva sus contratos Protobuf, repositorios, SQL y migraciones. Fase 0 documenta el mapa, ownership y criterios sin runtime; cada fase implementa y acepta las capacidades aplicables contra dependencias reales en el orden establecido por el roadmap.

El agente debe:
- Inventariar cada acción/endpoint y sus actores, precondiciones, invariantes y efectos persistidos/externos.
- Escribir la matriz de escenarios antes o junto con la implementación, incluyendo explícitamente números negativos/cero/límites cuando sean inputs posibles, correo/slug/documento duplicado, peticiones simultáneas, permisos insuficientes, sesión expirada, fallos de dependencia y ausencia de efectos parciales.
- Implementar pruebas unitarias, integración con dependencias reales, contratos y E2E según la frontera afectada. Los mocks no sustituyen aceptación de integración.
- Ejecutar las suites afectadas en CI; comprobar el workflow del commit exacto y todos los jobs/steps. No declarar aprobadas suites solo porque existan scripts o archivos de prueba.
- Desde Fase 0, documentar y establecer GitHub Rulesets, ramas/PR, CODEOWNERS, plantillas, CI base, scripts locales reproducibles, seguridad de workflows y matriz de pruebas. Los gates usan solo comandos aplicables a las herramientas reales.
- Adjuntar trazabilidad requisito→caso→test→ejecución al acta de fase. Registrar cada N/A con justificación previa y propietario.
- La Fase 8 corresponde a inteligencia empresarial según el roadmap ENSAMBRIA. El hardening y las pruebas transversales aplicables se realizan en cada fase; nunca se posponen las pruebas funcionales/negativas del comportamiento hasta una fase posterior.
Cada backend debe tener artefactos de build, imagen/binario, configuración de entorno, secretos, puertos/red y operación de despliegue propios; se ejecutan en VM/VPS independientes. El BFF público y cada frontend también se construyen y despliegan por separado. No se crea una imagen o unidad de despliegue que arranque varios backends. El workspace raíz compartido se usa durante compilación, no exige co-ubicación en producción. Mantén Dockerfiles, manifiestos de despliegue, configuración operativa y runbooks dentro del directorio del componente propietario cuando corresponda.

Una fase no puede declararse terminada si una prueba obligatoria falta, no se ejecutó o falla. Los agentes no deben declarar “100 %” por porcentaje de cobertura: el criterio es que todos los casos de uso definidos y sus particiones aplicables tengan evidencia aprobada. No se exige enumerar infinitas entradas posibles.
Si existe `compose.yaml` en la raíz, pertenece a servicios compartidos de infraestructura/desarrollo —PostgreSQL, Redis, NATS JetStream y observabilidad—, no a los procesos de los backends o frontends. Las aplicaciones no se deben agregar a ese Compose para producción ni sus imágenes se deben fusionar. Toda herramienta de observabilidad se configura según su documentación oficial y no debe bloquear operaciones de negocio si su destino remoto falla.

Desde el primer corte ejecutable de Fase 1, cada servicio Rust implementa las capacidades de observabilidad que le apliquen conforme a [ENSAMBRIA_Observability_Monitoring_Alerting_SLO.md](docs/rules/ENSAMBRIA_Observability_Monitoring_Alerting_SLO.md). Mantén logs seguros disponibles localmente y evita que una falla de exportación bloquee operaciones de negocio. La biblioteca compartida `crates/observability`, si es parte del diseño aprobado, estandariza primitivas técnicas sin poseer reglas ni datos de dominio. Prueba propagación, redacción y comportamiento ante fallos según los criterios de esa guía y del recorrido afectado.

En ENSAMBRIA, los adaptadores externos para facturación, notificaciones, pagos y proveedores especializados deben quedar desacoplados del núcleo del dominio. Mantén credenciales, callbacks, auditoría e historial separados por proveedor y por caso de uso. Los dominios deben llamar contratos neutrales al proveedor y el composition root o registro de dependencias debe gestionar los adapters; agregar o retirar uno no debe obligar a reescribir los otros módulos o las reglas de negocio.

## Gobernanza de instrucciones para agentes

Estas reglas aplican al coordinador y a todo agente/subagente que trabaje en ENSAMBRIA. Son instrucciones operativas y no sustituyen las fuentes normativas del proyecto.

### Flujo de consulta y resolución de conflictos

Estas instrucciones operativas dirigen al agente a [ARCHITECTURE_RULES.md](ARCHITECTURE_RULES.md). El contrato arquitectónico dirige al agente a [docs/requerimiento.md](docs/requerimiento.md) para visión, alcance, fases y aceptación del producto, y a [docs/arquitectura-dominios.md](docs/arquitectura-dominios.md) para ownership y diseño de dominios. Antes de planificar o realizar cualquier cambio, el agente debe consultar todos los documentos aplicables de [`docs/rules/`](docs/rules/); cada uno es normativo y obligatorio dentro de su materia. También debe revisar los ADR y documentación de fase que afecten el alcance.

Esta ruta de consulta no establece una precedencia global entre las fuentes. Se aplican conjuntamente dentro de su autoridad y ámbito: `ARCHITECTURE_RULES.md` define topología, fronteras y responsabilidades de ENSAMBRIA; `docs/requerimiento.md` define el producto, su alcance, fases y aceptación; `docs/arquitectura-dominios.md` detalla dominios y ownership; cada documento de `docs/rules/` establece requisitos obligatorios especializados; ADR aprobados registran decisiones en su alcance. El roadmap organiza la secuencia, sin anular ni reemplazar esas fuentes.

Si una instrucción específica del propietario propone cambiar una decisión normativa, solo puede hacerlo cuando identifique explícitamente la decisión aprobada; esta debe registrarse y reflejarse, mediante el proceso de gobierno, en las fuentes afectadas antes de implementar el alcance dependiente. Una propuesta de ADR no equivale a aprobación. Si dos fuentes aplicables presentan una contradicción real que no pueda resolverse por sus ámbitos, el agente debe documentarla, detener únicamente el trabajo afectado y solicitar una decisión del propietario; luego se armonizan las fuentes correspondientes. No se descarta silenciosamente ninguna regla ni se presume que una fuente prevalece globalmente por su posición en el flujo de consulta. Ningún agente puede conceder aprobación legal o especializada en nombre de su responsable.

### Ciclo y estados de trabajo

Todos los agentes siguen **CONSULTAR → INTERPRETAR → PLANIFICAR → IMPLEMENTAR → PROBAR → VALIDAR → DOCUMENTAR → REPORTAR** hasta donde lo permita su perfil y la tarea autorizada; un perfil de solo lectura no implementa ni edita. Deben identificar requisitos y reglas aplicables, owner, contratos/ADR y aceptación antes de actuar; convertirlos en cambios y pruebas verificables; y detener únicamente el trabajo afectado ante contradicciones o aprobaciones faltantes.

En cada informe, distinguir **REQUERIDO, DISEÑADO, IMPLEMENTADO, VALIDADO, APROBADO y BLOQUEADO**. Documentación, scaffolds, pruebas escritas o archivos de CI no demuestran por sí solos implementación, ejecución, aprobación ni efectividad del control. Reportar rutas normativas exactas, estado de ADR, componentes y ownership afectados, archivos cambiados, comandos/resultados reales, evidencia, N/A justificados y decisiones pendientes. No afirmar cumplimiento superior a la evidencia.

## Reglas de cumplimiento

- Sigue todas las fases y criterios aplicables del roadmap. Implementa cada dominio de extremo a extremo con persistencia/migraciones, reglas de negocio, API y contratos, validación, autorización, aislamiento tenant, errores, observabilidad, pruebas y documentación.
- Respeta los límites del monolito modular Rust: ownership único de dominio por backend/módulo, contratos gRPC para llamadas síncronas, eventos NATS JetStream/Outbox para comunicación asíncrona y BFF REST sin lógica de negocio.
- En cada fase/subfase de implementación, integra y verifica `frontend → HTTP/REST/OpenAPI → BFF → backend dueño → módulo propietario`. El BFF público separado llega a PUBLIC por gRPC; los BFF integrados de BUSINESS/PLATFORM usan contratos públicos internos, y CORE solo se consume mediante contratos internos/autorizados. Ningún frontend se comunica directamente con módulos, DB, Redis o NATS; ningún BFF accede directamente a esos almacenes.
- En cada fase y subfase, identifica los usos aplicables de Redis, NATS Core y NATS JetStream/Outbox según el dominio, además de PostgreSQL y gRPC. En la Fase 0 solo se documenta la aplicabilidad, sin agregar infraestructura runtime. Si un componente no aplica, registra antes de implementar una justificación concreta y verificable en el documento de la fase; no lo omitas por olvido ni lo agregues como refactor posterior. Redis se reserva exclusivamente para caché con TTL. NATS Core se usa para fan-out realtime efímero entre réplicas; NATS JetStream/Outbox, para eventos durables asíncronos. Ningún bus sustituye gRPC en consultas/comandos síncronos.
- Para secretos y certificados de workloads ENSAMBRIA, sigue la sección de Vault en [ARCHITECTURE_RULES.md](ARCHITECTURE_RULES.md): AppRole y ACL distintos por entorno/workload, KV v2 para secretos estáticos y PKI para certificados internos. ENSAMBRIA no debe leer, alterar ni rotar recursos pertenecientes a otros proyectos; no accedas ni cambies la VM/configuración compartida durante tareas documentales ni sin autorización explícita del operador.
- No guardes secretos, tokens de Vault, SecretID, certificados privados ni valores de credenciales en el repositorio, archivos de ejemplo, logs, trazas o respuestas. El runtime los obtiene en arranque/renovación controlada, no por petición HTTP.
- Usa una única base de datos PostgreSQL compartida por los cuatro backends. Cada módulo es dueño de su schema, tablas y migraciones versionadas; las migraciones se aplican coordinadamente. Los pools y credenciales son propios por proceso/backend y aplican grants mínimos. No permitas acceso cruzado ni JOINs SQL entre módulos.
- Separa roles de propietario/migración de credenciales de runtime. Aplica grants mínimos por backend/dominio y verifica que las credenciales de aplicación no lean/escriban schemas ajenos; compartir servidor, base o pool no justifica privilegios globales.
- Mantén independientes los frontends tenant, BUSINESS, móvil, administración global y Discovery. Consumen solo REST/OpenAPI/WebSocket de su BFF autorizado; nunca dependen directamente de gRPC, NATS, PostgreSQL, repositorios internos o proveedores.
- Conserva el control del backend propietario sobre identidad, permisos, tenants, cuotas y ciclo de vida de archivos. Usa el puerto neutral del módulo propietario del archivo y Cloudflare R2 mediante su API compatible con S3 como adapter inicial; nunca expongas credenciales permanentes y limita las autorizaciones temporales por alcance y expiración después de validar permisos.
- En todo dominio y capa, modela errores tipados y diagnosticables. Los logs internos deben incluir clase/código estable, componente, operación, dependencia y `correlation_id`/`trace_id`, además de metadatos seguros disponibles (por ejemplo SQLSTATE, constraint, tabla o columna); no reduzcas fallos a `error_type` genérico cuando hay detalles seguros. Nunca registres secretos, tokens, cookies, URL firmadas, contenido ni valores sensibles. El cliente recibe un envelope seguro y accionable, nunca SQL, stack trace o secretos. Prueba el mapeo módulo→gRPC→BFF HTTP y la redacción.
- El log final de status HTTP/gRPC no sustituye los eventos de diagnóstico de cada frontera. Registra eventos correlacionados de inicio, llamada a dependencia, fallo clasificado y respuesta final. Incluye nombre estable del evento, servicio/componente, operación, código/categoría, dependencia, resultado, duración propia de la dependencia y duración total, `correlation_id` y `trace_id`; solo marca retryable cuando la política lo confirme. El runtime debe extraer el contexto entrante de cada RPC en un span de servidor, no solo en readiness. Prueba automáticamente que los campos atraviesen BFF→gRPC→módulo y que datos sensibles no aparezcan. Cada prueba de aceptación debe comprobar que el evento específico de fallo operativo y el cierre HTTP comparten `correlation_id` y `trace_id` y que el cierre preserva el código/categoría; validar únicamente el status final incumple la regla.
- Esta regla es transversal y obligatoria en cada fase/subfase de implementación. La Fase 0 documenta las clases de error relevantes y las políticas previstas, sin introducir código/runtime. Las fases de implementación prueban errores de validación, autorización, conflicto, timeout/conectividad, persistencia y proveedores aplicables, con contexto estructurado y mensajes/detalles seguros en REST/frontend. Documenta qué clases aplican y justifica las no aplicables. No declares una fase completa si los errores están silenciados, sin contexto, mal mapeados o sin recuperación clara.

## Integración realtime transversal obligatoria

Esta regla es transversal y obligatoria **en cada fase y subfase de implementación**, sin excepciones por dominio, prioridad, frontend o etapa. La Fase 0 documental evalúa y registra la aplicabilidad, pero no implementa realtime. Antes de implementar cada fase/subfase, documenta cómo aplicará la sincronización en tiempo real y cómo se recuperará el estado; durante esa misma fase/subfase implementa y verifica la parte que corresponda. No se permite posponerla a una fase posterior, limitarla a notificaciones o algunas pantallas, ni dejarla como refactor futuro.

Para cada cambio de estado persistido que pueda ser visible para usuarios u operadores, integra en la misma entrega Outbox versionado del módulo dueño → NATS JetStream → gateway realtime modular; para fan-out efímero entre réplicas, usa NATS Core → WebSocket autenticado por BFF → coordinador central TanStack Query en tenant/admin → recuperación REST autorizada por cursor/snapshot. Toda fase/subfase de implementación debe evaluar también cambios de autenticación, permisos, configuración, facturación, tareas, biblioteca, operaciones y administración; si un cambio no debe emitir o consumir eventos realtime, registra la justificación concreta y verificable en su matriz de integración antes de implementar. La Fase 0 registra que no crea ni modifica estado persistido visible.

Mantén `event_id`, cursor durable, versión de agregado, audiencia/scope, deduplicación, orden, detección de huecos, reconexión, permisos y sincronización manual de recuperación. Diseña desde el inicio para múltiples réplicas de BFF/runtime/NATS Core/JetStream/Redis/PostgreSQL/frontend: NATS Core hace fan-out efímero entre réplicas, JetStream conserva el replay durable, PostgreSQL es fuente de verdad y Redis se usa solo como caché TTL. No uses sticky sessions ni memoria local como autoridad; las señales Core perdidas se recuperan mediante cursor/snapshot autorizado. El gateway es un módulo del mismo monolito modular, expone contratos gRPC internos y no es otro microservicio; el BFF no accede directamente a Redis/NATS/PostgreSQL. Cada entrega que cruce backend y frontend debe completar ambos extremos del contrato en la misma fase/subfase o dejar documentado el bloqueo real que impide cerrarla; no declares la fase completa mientras ese criterio siga pendiente.

### Recuperación obligatoria de Redis y JetStream

En toda fase/subfase que use Redis o NATS, implementa y prueba reconexión tras reinicio: Redis `ConnectionManager` con backoff acotado para reanudar caché; suscriptores NATS Core se reconectan y re-suscriben, aceptando que sus señales no son durables; consumidores JetStream reconstruyen su consumer durable y recuperan mensajes pendientes sin perder idempotencia. El journal PostgreSQL/Outbox, JetStream y la consulta REST por cursor reparan señales efímeras perdidas. Añade pruebas con PostgreSQL, Redis y NATS reales. Los tests destructivos de reinicio solo pueden apuntar a los servicios de desarrollo definidos en `backend/.env`, no crean contenedores y nunca ejecutan contra producción. Documenta el comando y el efecto de reinicio antes de ejecutar esos tests.
