# Registro de Fase 1: Fundación de CORE

## Estado vigente

**Fase 1: ABIERTA y NO ACEPTADA.** El runtime de fundamento de CORE está integrado en `main` mediante el PR #4. El commit de merge `502ba20e144ad384fcf1f8d318680fa17b98b2ec` pasó `repository-quality` y `security-dependencies` en el run [44469108807](https://github.com/programadorkevinsvega-sys/ENSAMBRIA/actions/runs/44469108807), incluida la suite PostgreSQL efímera. El propietario autorizó ahora configurar el despliegue automático de staging para CORE; esta configuración y su primera ejecución en la VM aún están pendientes. La fase no se declara aceptada.

**Subfase 1.1:** el propietario autorizó iniciar su trabajo el 2026-11-18 mientras Fase 0 continúa abierta. El alcance de producto sigue limitado al fundamento técnico, sin rutas ni operaciones de negocio. CORE implementa el protocolo gRPC Health Checking `grpc.health.v1`: liveness no depende de PostgreSQL y readiness comprueba PostgreSQL; ambos listeners son loopback, no APIs de producto. El propietario autorizó el 2026-11-19 configurar CD para desplegar CORE automáticamente en staging tras un CI exitoso en `main` y aplicar allí las migraciones automáticamente. GitHub construirá y enviará únicamente los binarios y archivos SQL de migración, nunca el código fuente ni `.env`; la credencial restringida del migrator permanece provisionada en la VM y separada de la credencial de runtime. La VM reportada es Ubuntu x86_64, ya está en Tailscale y tiene Tailscale SSH habilitado. Esta autorización no permite al agente conectarse o modificar la VM, sus reglas de red, Nginx, Cloudflare Tunnel ni las VMs de PostgreSQL, Redis o NATS. No se enviará telemetría externa.

La implementación incluye configuración PostgreSQL por entorno, pool SQLx acotado, errores seguros, `tracing`, métricas Prometheus locales, health gRPC, contexto tenant por transacción, migración versionada y runner separado. El rol de runtime no puede crear objetos ni leer el historial SQLx. El código y sus pruebas están integrados en `main`; staging no se ha consultado ni modificado. No hay tablas tenant-scoped/RLS de producto ni exportación OpenTelemetry/Sentry. Los ADR conservan el estado expresado en cada documento y siguen siendo normativos dentro de su alcance hasta que una decisión aprobada los sustituya.

Las descripciones de objetivos alcanzados, rutas de código, migraciones, conteos de pruebas y comandos de ejecución que aparecían en versiones anteriores de este registro quedan retiradas como evidencia vigente. No deben utilizarse para afirmar que una subfase está implementada, validada o aceptada. El estado común y los criterios de aceptación están en [ROADMAP.md](../ROADMAP.md) y [docs/requerimiento.md, §§22–23](requerimiento.md).

## Alcance requerido

La Fase 1 implementará, según la secuencia del roadmap y en los owners correspondientes:

- La base técnica y composición legítima del workspace Cargo al incorporar código funcional.
- Persistencia PostgreSQL compartida, ownership de schemas y migraciones, credenciales de mínimo privilegio y aislamiento tenant-scoped.
- Identidad, autenticación, autorización, tenancy y contexto de producto.
- El flujo durable CORE→PLATFORM para el alta operativa del tenant, con Outbox/Inbox cuando corresponda.
- Suscripciones SaaS y evaluación de entitlements conforme a los límites de CORE y PLATFORM.
- Reservas y disponibilidad común bajo el ownership establecido.
- APIs/BFF, observabilidad, privacidad, seguridad y pruebas de aceptación aplicables a cada recorrido introducido.

Este resumen no sustituye los criterios normativos del [requerimiento](requerimiento.md), el [contrato arquitectónico](../ARCHITECTURE_RULES.md), los ADR ni las reglas especializadas.

## Subfase 1.1 — matriz previa de integraciones y aceptación

**Alcance aprobado por el propietario el 2026-11-18:** fundamento técnico de CORE y PostgreSQL; no introducir rutas de producto, alta operativa de tenants, cambios de estado de negocio ni eventos artificiales. El propietario autorizó el 2026-11-19 preparar el despliegue automático de staging descrito abajo. Se conserva el workspace Cargo único. Health gRPC sigue siendo una interfaz operativa interna de loopback. La prueba de fallo readiness pasó en CI para el commit de merge `502ba20`; staging aún no se ha desplegado.

### Criterios de aceptación de 1.1

1. Workspace raíz y composición funcional sin paquetes, targets o tablas placeholder.
2. Pool y configuración implementados conforme a ADR-0001 y a la guía PostgreSQL, con errores seguros, proceso ejecutable y migración versionada. Runtime y migrator son identidades separadas, con grants mínimos verificados en PostgreSQL real.
3. Pruebas PostgreSQL reales ejecutadas localmente en un servicio efímero y en CI para los comportamientos implementados, incluidas migración, roles/grants, health, métricas y contexto transaccional. La primera aceptación del CD requiere una ejecución real de staging; esa ejecución aún está pendiente.
4. N/A de HTTP/BFF de producto, Redis, NATS, Outbox/Inbox, realtime y rutas SEO limitados explícitamente al alcance 1.1; el health gRPC operativo se acepta por separado y ningún N/A cuenta como capacidad implementada.
5. Pruebas unitarias, compilación, formato, lints y CI aplicables ejecutados; el PR #4 está integrado y los checks del commit de merge pasaron. No consta una revisión independiente en GitHub.
6. El contexto transaccional se implementa y valida con PostgreSQL real; la ausencia de tablas tenant-scoped en 1.1 no se presenta como aceptación de RLS. Las políticas y pruebas negativas de datos tenant pertenecen a la subfase que introduce esas filas.
7. El cierre global de Fase 1 permanece pendiente de requisitos que no pertenecen a 1.1, incluidos el flujo durable de 1.3 y la capacidad SEO base que aún requiere armonización documental.
8. El workflow de CD solo despliega tras CI exitoso de `main` y transfiere exclusivamente binarios y SQL. Aplica automáticamente las migraciones en staging con la identidad restringida local, reinicia CORE, valida health/readiness y restaura el binario anterior ante fallos de migración o readiness. Las migraciones ya confirmadas en PostgreSQL no se revierten automáticamente y deben ser compatibles con la versión anterior. La aceptación queda pendiente de configuración externa y primera ejecución real; no habilitar tráfico público.

## Aceptación pendiente

La aceptación requiere implementación real por recorrido, pruebas aplicables ejecutadas contra las dependencias reales, validación local y CI según las fuentes vigentes, documentación sincronizada y evidencia trazable conforme a §23 del requerimiento. Una decisión arquitectónica o una descripción en este registro no prueba implementación.
