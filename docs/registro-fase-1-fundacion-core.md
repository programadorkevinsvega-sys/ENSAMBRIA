# Registro de Fase 1: Fundación de CORE

## Estado vigente

**Fase 1: ABIERTA y NO ACEPTADA.** El código y los artefactos de implementación asociados a registros anteriores fueron retirados durante el reinicio del repositorio. En la rama actual existe un workspace Cargo y `ensambria-core` implementa carga de configuración PostgreSQL, pool acotado, errores seguros y contexto tenant transaccional. Las pruebas unitarias se ejecutan localmente; las pruebas PostgreSQL reales están escritas para CI pero aún no se ha verificado su ejecución remota.

**Subfase 1.1:** el propietario autorizó iniciar su trabajo el 2026-11-18 mientras Fase 0 continúa abierta. Esta autorización es acotada a 1.1: no cierra ni acepta Fase 0, no habilita 1.2, no autoriza integrar cambios sin los controles/revisiones aplicables y no autoriza acceder, modificar o desplegar en staging. El alcance aprobado para 1.1 es fundamento técnico sin recorridos de producto; la matriz previa de integraciones y sus N/A concretos aparece más adelante. La implementación está en curso y no se acepta aún.

La implementación parcial incluye configuración de proceso por variables de entorno, pool SQLx acotado, errores seguros, diagnóstico `tracing` y contexto tenant local a transacción. No hay proceso ejecutable/composition root, migraciones de CORE, credenciales productivas o grants de schema verificados, políticas RLS aplicadas a tablas tenant-scoped ni runtime de métricas/health/exportación. Las pruebas PostgreSQL están implementadas y compiladas, pero su ejecución remota en CI sigue pendiente; no se ejecutaron contra staging. El propietario confirmó que la base configurada es staging, pero no autorizó el acceso. La rama no incorpora rutas de producto, tablas tenant-scoped ni eventos de negocio. Esto no revoca las decisiones arquitectónicas aceptadas en Fase 0 o ratificadas para el diseño de Fase 1. Los ADR conservan el estado expresado en cada documento y siguen siendo normativos dentro de su alcance hasta que una decisión aprobada los sustituya.

Las descripciones de objetivos alcanzados, rutas de código, migraciones, conteos de pruebas y comandos de ejecución que aparecían en versiones anteriores de este registro quedan retiradas como evidencia vigente. No deben utilizarse para afirmar que una subfase está implementada, validada o aceptada. El estado común y los criterios de aceptación están en [ROADMAP.md](../ROADMAP.md) y [docs/requerimiento.md, §§22–23](requerimiento.md).

## Alcance requerido

La Fase 1 implementará, según la secuencia del roadmap y en los owners correspondientes:

- La base técnica y composición legítima del workspace Cargo al incorporar código funcional.
- Persistencia PostgreSQL compartida, ownership de schemas y migraciones, credenciales de mínimo privilegio y aislamiento tenant-scoped.
- Identidad, autenticación, autorización, tenancy y contexto de producto.
- El flujo durable CORE→PLATFORM para el alta operativa del tenant, con Outbox/Inbox cuando corresponda.
- Suscripciones SaaS y evaluación de entitlements conforme a los límites de CORE y PLATFORM.
- Reservas y disponibilidad común bajo el ownership establecido.
- APIs/BFF, observabilidad, privacidad, seguridad y pruebas de aceptación aplicables a cada recorrido introducido.

Este resumen no sustituye los criterios normativos del [requerimiento](requerimiento.md), el [contrato arquitectónico](../ARCHITECTURE_RULES.md), los ADR ni las reglas especializadas.

## Subfase 1.1 — matriz previa de integraciones y aceptación

**Alcance aprobado por el propietario el 2026-11-18:** fundamento técnico de CORE y PostgreSQL; no introducir rutas de producto, alta operativa de tenants, cambios de estado de negocio ni eventos artificiales. Esta matriz antecede a cualquier código. Se conserva el único workspace Cargo en la raíz y no se crean paquetes/targets vacíos. Los controles aplicables a un runtime real se implementan y prueban en el mismo corte; no se declara aceptación de métricas/health/exportación cuando aún no existe un proceso.

|---|---|---|

El workspace no fusiona despliegues ni autoriza crates placeholder. La selección de forma virtual o paquete raíz se resuelve conforme a ADR-0003 al definir el primer target ejecutable real. | `cargo metadata` debe mostrar el workspace y miembros reales. ### Criterios de aceptación de 1.1

1. Workspace raíz y composición funcional sin paquetes, targets o tablas placeholder.
2. Pool y configuración implementados conforme a ADR-0001 y a la guía PostgreSQL, con errores seguros y configuración no secreta validable. Quedan pendientes runtime, roles/grants de despliegue y migraciones de CORE.
3. Pruebas PostgreSQL reales ejecutadas en el servicio efímero de CI para los comportamientos implementados; las pruebas locales solo compilan el target de integración. No se accede a staging.
4. N/A de HTTP/BFF, gRPC, Redis, NATS, Outbox/Inbox, realtime y rutas SEO limitados explícitamente al alcance 1.1; ningún N/A cuenta como capacidad implementada.
5. Pruebas unitarias, compilación, formato, lints y CI aplicables ejecutados; revisión del diff/secrets y PR conforme al gobierno vigente.
6. El contexto transaccional se implementa y valida con PostgreSQL real; la ausencia de tablas tenant-scoped en 1.1 no se presenta como aceptación de RLS. Las políticas y pruebas negativas de datos tenant pertenecen a la subfase que introduce esas filas.
7. El cierre global de Fase 1 permanece pendiente de requisitos que no pertenecen a 1.1, incluidos el flujo durable de 1.3 y la capacidad SEO base que aún requiere armonización documental.

## Aceptación pendiente

La aceptación requiere implementación real por recorrido, pruebas aplicables ejecutadas contra las dependencias reales, validación local y CI según las fuentes vigentes, documentación sincronizada y evidencia trazable conforme a §23 del requerimiento. Una decisión arquitectónica o una descripción en este registro no prueba implementación.
