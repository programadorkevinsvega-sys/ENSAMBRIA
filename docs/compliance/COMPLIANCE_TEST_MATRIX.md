# Matriz inicial de controles, pruebas y evidencia

> **BORRADOR TEMPORAL — ENSAMBRIA — PENDIENTE DE REVISIÓN Y APROBACIÓN POR ABOGADO COMPETENTE EN COLOMBIA.**

> **Estado:** diseño de pruebas de Fase 0; no existen servicios, aplicaciones ni ejecuciones de aceptación de producto. Cada owner debe convertir las filas aplicables en pruebas automatizadas de la misma fase que introduce el tratamiento. No se declara cumplimiento por la existencia de esta matriz.

Esta matriz enlaza los requisitos del [registro de tratamientos](DATA_PROCESSING_REGISTER.md), las diez capacidades de [docs/requerimiento.md, sección 14](../requerimiento.md) y las fuentes de [privacidad legal](../rules/ENSAMBRIA_Privacy_Legal_Compliance.md), [PDLM](../rules/ENSAMBRIA_Privacy_Data_Lifecycle_Management.md), [calidad](../rules/ENSAMBRIA_prompt_maestro_enterprise_quality_engineering.md), [frontend](../rules/ENSAMBRIA_frontend_security_accessibility_ux_ui_performance_observability_rules.md) y [k6](../rules/ENSAMBRIA_k6_performance_load_stress_and_capacity_testing_rules.md).

## Evidencia y trazabilidad

Para cada prueba se conservará: ID de requisito/caso, owner, versión del contrato, datos sintéticos/autorizados, ambiente, dependencias, comando exacto, commit, resultado, artefactos redactados y defectos/bloqueos. Un test escrito no equivale a test ejecutado; una ejecución local no sustituye el check remoto del PR; una prueba con mock no sustituye la aceptación de una frontera que requiere dependencia real.

Los valores legales, plazos, bases, roles, thresholds y mercados no se parametrizan hasta que sus decisiones estén validadas. Si un control o prueba no aplica, el owner registra previamente justificación y evidencia. Cada fase actualiza esta matriz en el mismo cambio que introduce el comportamiento y no difiere pruebas negativas o de resiliencia a una fase de hardening posterior.
