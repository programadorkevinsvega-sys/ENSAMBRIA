# Registro de Fase 1: Fundación de CORE

## Estado vigente

**Fase 1: ABIERTA y NO ACEPTADA.** El código y los artefactos de implementación asociados a registros anteriores fueron retirados durante el reinicio del repositorio. En la rama actual existe un workspace Cargo y `ensambria-core` implementa configuración PostgreSQL, pool acotado, errores seguros, contexto tenant transaccional, proceso ejecutable, health gRPC, métricas locales y un runner de migraciones con roles separados. Las pruebas unitarias y de integración PostgreSQL pasaron localmente contra PostgreSQL 17 efímero; el run de CI del commit `4c298f7` también pasó. La aceptación de 1.1 sigue pendiente de revisión independiente.

**Subfase 1.1:** el propietario autorizó iniciar su trabajo el 2026-11-18 mientras Fase 0 continúa abierta. Esta autorización es acotada a 1.1: no cierra ni acepta Fase 0, no habilita 1.2 ni autoriza integrar cambios sin los controles/revisiones aplicables. El propietario autorizó después el acceso a staging; antes de usarlo se verificará el destino y se limitarán las comprobaciones a consultas de lectura y contexto local a transacción, sin migraciones ni cambios persistentes. El alcance aprobado para 1.1 es fundamento técnico sin recorridos de producto; la matriz previa de integraciones y sus N/A concretos aparece más adelante. Para salud operativa se implementa el protocolo estándar gRPC Health Checking `grpc.health.v1`: liveness no depende de PostgreSQL y readiness comprueba PostgreSQL con timeout acotado; los listeners son internos y de loopback, no APIs de producto. El diseño no autoriza desplegar ni enviar telemetría a servicios externos. La implementación sigue en curso y no se acepta aún.

La implementación incluye configuración de proceso por variables de entorno, pool SQLx acotado, errores seguros, diagnóstico `tracing`, métricas Prometheus locales, health gRPC, contexto tenant local a transacción y migraciones versionadas. El binario CORE y su apagado ordenado pasaron prueba de proceso contra PostgreSQL real. El runner de migraciones exige `core_migrator` sin privilegios de superusuario/CREATE DATABASE/CREATE ROLE y asume `core_schema_owner`; el rol de runtime recibe solo USAGE del schema y no puede crear objetos ni leer metadatos de migración. El bootstrap, las migraciones y las pruebas de permisos pasaron localmente contra PostgreSQL 17 efímero y en el CI del commit `4c298f7`. No hay políticas RLS aplicadas a tablas tenant-scoped ni exportación OpenTelemetry/Sentry. Las pruebas PostgreSQL previas de `52f2c81` son evidencia histórica y no sustituyen la ejecución actual. Staging todavía no se ha consultado ni modificado. La rama no incorpora rutas de producto, tablas tenant-scoped ni eventos de negocio. Esto no revoca las decisiones arquitectónicas aceptadas en Fase 0 o ratificadas para el diseño de Fase 1. Los ADR conservan el estado expresado en cada documento y siguen siendo normativos dentro de su alcance hasta que una decisión aprobada los sustituya.

Las descripciones de objetivos alcanzados, rutas de código, migraciones, conteos de pruebas y comandos de ejecución que aparecían en versiones anteriores de este registro quedan retiradas como evidencia vigente. No deben utilizarse para afirmar que una subfase está implementada, validada o aceptada. El estado común y los criterios de aceptación están en [ROADMAP.md](../ROADMAP.md) y [docs/requerimiento.md, §§22–23](requerimiento.md).

## Alcance requerido

La Fase 1 implementará, según la secuencia del roadmap y en los owners correspondientes:

- La base técnica y composición legítima del workspace Cargo al incorporar código funcional.
- Persistencia PostgreSQL compartida, ownership de schemas y migraciones, credenciales de mínimo privilegio y aislamiento tenant-scoped.
- Identidad, autenticación, autorización, tenancy y contexto de producto.
- El flujo durable CORE→PLATFORM para el alta operativa del tenant, con Outbox/Inbox cuando corresponda.
- Suscripciones SaaS y evaluación de entitlements conforme a los límites de CORE y PLATFORM.
- Reservas y disponibilidad común bajo el ownership establecido.
- APIs/BFF, observabilidad, privacidad, seguridad y pruebas de aceptación aplicables a cada recorrido introducido.

Este resumen no sustituye los criterios normativos del [requerimiento](requerimiento.md), el [contrato arquitectónico](../ARCHITECTURE_RULES.md), los ADR ni las reglas especializadas.

## Subfase 1.1 — matriz previa de integraciones y aceptación

**Alcance aprobado por el propietario el 2026-11-18:** fundamento técnico de CORE y PostgreSQL; no introducir rutas de producto, alta operativa de tenants, cambios de estado de negocio ni eventos artificiales. Esta matriz antecede a cualquier código. Se conserva el único workspace Cargo en la raíz y no se crean paquetes/targets vacíos. Para salud operativa se adopta el protocolo estándar gRPC Health Checking `grpc.health.v1`: liveness no depende de PostgreSQL y readiness verifica PostgreSQL; el listener es interno y de loopback, no una API de producto. El diseño no autoriza desplegar ni enviar telemetría a servicios externos. La implementación técnica de 1.1 se validó localmente y en CI; queda pendiente su revisión independiente.

### Criterios de aceptación de 1.1

1. Workspace raíz y composición funcional sin paquetes, targets o tablas placeholder.
2. Pool y configuración implementados conforme a ADR-0001 y a la guía PostgreSQL, con errores seguros, proceso ejecutable y migración versionada. Runtime y migrator son identidades separadas, con grants mínimos verificados en PostgreSQL real.
3. Pruebas PostgreSQL reales ejecutadas localmente en un servicio efímero y en CI para los comportamientos implementados en esta rama, incluidas migración, roles/grants, health, métricas y contexto transaccional. No se accede a staging.
4. N/A de HTTP/BFF de producto, Redis, NATS, Outbox/Inbox, realtime y rutas SEO limitados explícitamente al alcance 1.1; el health gRPC operativo se acepta por separado y ningún N/A cuenta como capacidad implementada.
5. Pruebas unitarias, compilación, formato, lints y CI aplicables ejecutados; revisión del diff/secrets y PR conforme al gobierno vigente.
6. El contexto transaccional se implementa y valida con PostgreSQL real; la ausencia de tablas tenant-scoped en 1.1 no se presenta como aceptación de RLS. Las políticas y pruebas negativas de datos tenant pertenecen a la subfase que introduce esas filas.
7. El cierre global de Fase 1 permanece pendiente de requisitos que no pertenecen a 1.1, incluidos el flujo durable de 1.3 y la capacidad SEO base que aún requiere armonización documental.

## Aceptación pendiente

La aceptación requiere implementación real por recorrido, pruebas aplicables ejecutadas contra las dependencias reales, validación local y CI según las fuentes vigentes, documentación sincronizada y evidencia trazable conforme a §23 del requerimiento. Una decisión arquitectónica o una descripción en este registro no prueba implementación.
